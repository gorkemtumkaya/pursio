# Requirements Document

## Introduction

This feature lets the user type any hobby on the start screen and get a Skill_Tree for it, generated by an LLM and rendered by the existing Path_View from the `skill-path-ui` spec. A Nuxt server route, `POST /api/tree`, calls the LLM with the Generation_Prompt from `server/prompts/skill-tree.md`, checks the answer with the existing Tree_Schema (`parseSkillTree` in `shared/utils/skill-tree-schema.ts`) and Tree_Validator (`validateSkillTree` in `shared/utils/skill-tree-validate.ts`), combined by `loadSkillTree` in `shared/utils/skill-tree-load.ts`, retries once on invalid output, caches results in server memory and rate-limits generations per IP.

A Settings page lets the user pick Anthropic or OpenAI, a model and their own API key. The settings stay in this browser's localStorage. Every LLM request goes through the Pursio server; the browser never calls a provider directly. Without a user key, the server uses its default provider, model and key from `.env`.

The demo at `/path?demo=1` keeps showing the Sample_Tree.

Scope limits: the implementation plan has at most 7 tasks. Automated tests cover logic only (pure functions and server modules with mocked providers); there are no UI component tests. No new dependency is in scope: provider calls use the HTTP client that ships with Nuxt, and the JSON schema sent to the provider is derived from the existing Tree_Schema with zod's built-in JSON Schema export.

### Out of scope

Supabase storage of trees, accounts, multiple saved generated trees, streaming output, providers other than Anthropic and OpenAI, persistent or shared caches across server instances, and changes to the Generation_Prompt text.

## Glossary

- **Skill_Tree, Section, Node, Main_Node, Side_Quest_Node, Milestone_Node, Sample_Tree, Tree_Schema, Tree_Validator, Validation_Error, Progress, Progress_Store, Path_View**: As defined in the `skill-path-ui` spec.
- **Tree_Loader**: The existing `loadSkillTree` function, which runs the Tree_Schema and then the Tree_Validator and returns either a Skill_Tree or a list of Validation_Errors. `formatValidationError` turns one Validation_Error into one line of text.
- **Tree_Route**: The Nuxt server route `POST /api/tree`.
- **Test_Route**: The Nuxt server route that runs a connection test for the LLM settings.
- **Generator**: The server module that turns a hobby and a Provider_Config into a Generation_Result: it calls a Provider_Adapter, checks the answer with the Tree_Loader and retries once.
- **Provider_Adapter**: One server module per LLM provider implementing the single function `generateTree(hobby, { provider, model, apiKey })` used by the Generator. Adapters exist for `anthropic` and `openai`.
- **Provider_Config**: The triple of `provider` (`anthropic` or `openai`), `model` (model id string) and `apiKey` used for one LLM call.
- **Default_Config**: The Provider_Config read on the server from the `.env` keys `NUXT_LLM_PROVIDER`, `NUXT_LLM_MODEL` and `NUXT_LLM_API_KEY` through Nuxt server-only runtime config.
- **User_Config**: The Provider_Config the browser sends with a request when LLM_Settings contain a non-empty API key.
- **Key_Header**: The HTTP request header `x-llm-api-key` that carries the User_Config API key from the browser to the Tree_Route or Test_Route.
- **Generation_Prompt**: The text of `server/prompts/skill-tree.md`, used as the LLM system prompt without changes.
- **Generation_Schema**: The JSON schema sent to the provider as the structured output or tool schema. The Generation_Schema accepts either a Skill_Tree or the Not_A_Hobby_Signal.
- **Not_A_Hobby_Signal**: The LLM answer `{"error":"not_a_hobby"}` that the Generation_Prompt asks for when the input is not a real hobby.
- **Generation_Result**: The outcome of one Generator run: a Skill_Tree with the model id used, the Not_A_Hobby_Signal, or an Error_Code.
- **Error_Code**: One of `invalid_input`, `not_a_hobby`, `rate_limited`, `timeout`, `generation_failed`, `provider_auth`, `provider_error` or `no_key`, returned by the Tree_Route and Test_Route as `{ "error": <code> }`.
- **Normalized_Hobby**: The hobby input trimmed of leading and trailing whitespace, with inner runs of whitespace collapsed to one space, and lowercased.
- **Tree_Cache**: The in-memory map on the server from Cache_Key to a generated Skill_Tree and the model id that produced the Skill_Tree.
- **Cache_Key**: The combination of Normalized_Hobby, provider and model of the Provider_Config used.
- **Rate_Limiter**: The in-memory server module that counts Billable_Generations per client IP in a sliding 60-minute window.
- **Billable_Generation**: One Tree_Route request that uses the Default_Config and misses the Tree_Cache. A Generator run that retries counts once.
- **Start_Screen**: The page at `/` (`app/pages/index.vue`) with the hobby input.
- **Example_Chip**: A button on the Start_Screen that fills in and submits an example hobby: "bouldering", "film photography" or "guitar".
- **Generating_State**: The Start_Screen state shown while a Tree_Route request is in flight, with the text "Building your skill tree…".
- **Generated_Tree**: The last Skill_Tree returned by the Tree_Route, saved in localStorage together with the model id that produced the Skill_Tree.
- **Model_Label**: The small text "Generated with <model id>" shown under a Generated_Tree in the Path_View.
- **Settings_Page**: The page at `/settings`.
- **LLM_Settings**: The provider, model id and API key the user saved on the Settings_Page, stored in this browser's localStorage only.
- **Model_Preset**: One entry of the fixed list of model ids offered per provider on the Settings_Page, kept in one shared file.
- **Friendly_Message**: A one-sentence, non-technical message shown in the UI for an Error_Code, with no stack trace, provider response body or API key.

## Requirements

### Requirement 1: Tree route input

**User Story:** As a learner, I want to type any hobby and have it accepted or clearly rejected, so that I know right away whether my input works.

#### Acceptance Criteria

1. THE Tree_Route SHALL accept a POST request with a JSON body `{ "hobby": <string> }` and SHALL trim leading and trailing whitespace from `hobby` before any other check.
2. IF the request body has no `hobby` string, or the trimmed `hobby` is empty or longer than 60 characters, THEN THE Tree_Route SHALL respond with HTTP status 400 and `{ "error": "invalid_input" }` without calling a Provider_Adapter.
3. THE Normalized_Hobby function SHALL be a pure function, and FOR ALL input strings, normalizing an already Normalized_Hobby SHALL return the same string (idempotence property).
4. FOR ALL pairs of hobby inputs that differ only in letter case, leading or trailing whitespace, or the length of inner whitespace runs, THE Normalized_Hobby function SHALL return equal strings (property).

### Requirement 2: Provider configuration and API key handling

**User Story:** As a learner, I want the app to work without setup and also with my own key, so that I can try it at once and control which model I use.

#### Acceptance Criteria

1. WHEN a Tree_Route or Test_Route request carries a non-empty Key_Header, THE route SHALL use the User_Config built from the Key_Header value and the `provider` and `model` fields of the request body.
2. WHEN a Tree_Route request carries no Key_Header or an empty Key_Header, THE Tree_Route SHALL use the Default_Config and SHALL ignore any `provider` and `model` fields in the request body.
3. IF a request with a non-empty Key_Header has a `provider` other than `anthropic` or `openai`, or a `model` that is empty or longer than 100 characters after trimming, THEN THE route SHALL respond with HTTP status 400 and `{ "error": "invalid_input" }` without calling a Provider_Adapter.
4. IF the Tree_Route must use the Default_Config and `NUXT_LLM_API_KEY`, `NUXT_LLM_MODEL` or `NUXT_LLM_PROVIDER` is empty or `NUXT_LLM_PROVIDER` is neither `anthropic` nor `openai`, THEN THE Tree_Route SHALL respond with HTTP status 503 and `{ "error": "no_key" }`.
5. THE Default_Config values SHALL be read only on the server through Nuxt server-only runtime config, and THE client bundle and every route response SHALL exclude the Default_Config API key.
6. THE Tree_Route and Test_Route SHALL use a User_Config API key only for the provider calls of the same request, and SHALL exclude the key from logs, the Tree_Cache, error responses and any other server-side storage.
7. THE `.env.example` file SHALL list `NUXT_LLM_PROVIDER`, `NUXT_LLM_MODEL` and `NUXT_LLM_API_KEY` with placeholder values.

### Requirement 3: Provider interface and LLM call

**User Story:** As a developer, I want each provider behind one small interface, so that adding a provider later means adding one file.

#### Acceptance Criteria

1. THE Generator SHALL call providers only through the Provider_Adapter function `generateTree(hobby, { provider, model, apiKey })`, and THE Generator SHALL select the Provider_Adapter by the `provider` value through one lookup map.
2. THE Generator SHALL load the Generation_Prompt from `server/prompts/skill-tree.md` and SHALL pass the file text unchanged as the system prompt of every provider call, with the trimmed hobby as the user message.
3. THE Provider_Adapter for each provider SHALL request structured JSON output from the provider (structured output or tool calling) constrained by the Generation_Schema, and SHALL return the parsed JSON value to the Generator.
4. THE Generation_Schema SHALL be derived from the Tree_Schema in code, so that a change to the Tree_Schema changes the Generation_Schema without a separate edit.
5. IF the provider responds with HTTP status 401 or 403, THEN THE Provider_Adapter SHALL report a `provider_auth` failure to the Generator.
6. IF the provider responds with any other non-success status, a network failure, or an answer that is not parseable JSON, THEN THE Provider_Adapter SHALL report a `provider_error` failure to the Generator, with a message that excludes the API key.

### Requirement 4: Response validation and retry

**User Story:** As a learner, I want the path I get to always work, so that I never see a broken or unlockable tree.

#### Acceptance Criteria

1. WHEN a Provider_Adapter returns a JSON value other than the Not_A_Hobby_Signal, THE Generator SHALL check the value with the Tree_Loader.
2. WHEN the Tree_Loader accepts the value, THE Generator SHALL return a Generation_Result holding the Skill_Tree and the model id of the Provider_Config used.
3. IF the Tree_Loader rejects the first answer, or the first answer is not parseable JSON, THEN THE Generator SHALL call the Provider_Adapter exactly one more time, with a retry message that lists the Validation_Errors as lines from `formatValidationError`, at most 20 lines.
4. IF the Tree_Loader rejects the second answer, or the second answer is not parseable JSON, THEN THE Generator SHALL return the Error_Code `generation_failed`, and THE Tree_Route SHALL respond with HTTP status 502 and `{ "error": "generation_failed" }`.
5. WHEN the Tree_Route returns a Skill_Tree, THE Tree_Route SHALL respond with HTTP status 200 and `{ "tree": <Skill_Tree>, "model": <model id> }`.
6. FOR ALL sequences of mocked provider answers, THE Generator SHALL call the Provider_Adapter at most 2 times per Tree_Route request (property).
7. FOR ALL Skill_Trees returned by the Generator, the Tree_Loader SHALL accept the Skill_Tree with zero Validation_Errors (invariant property).

### Requirement 5: Not a hobby

**User Story:** As a learner who typed something that isn't a hobby, I want a friendly hint, so that I know to try something else.

#### Acceptance Criteria

1. WHEN a Provider_Adapter returns the Not_A_Hobby_Signal, THE Generator SHALL return the Not_A_Hobby_Signal without a retry.
2. WHEN the Generator returns the Not_A_Hobby_Signal, THE Tree_Route SHALL respond with HTTP status 422 and `{ "error": "not_a_hobby" }`.
3. WHEN the Start_Screen receives `{ "error": "not_a_hobby" }`, THE Start_Screen SHALL show the Friendly_Message "That doesn't look like a hobby yet. Try something you can practice, like bouldering or guitar." and SHALL keep the typed input.
4. THE Tree_Cache SHALL store only Skill_Trees, so that a Not_A_Hobby_Signal or an Error_Code is generated again on the next request.

### Requirement 6: Result cache

**User Story:** As a demo presenter, I want a hobby I already generated to come back instantly, so that repeat demos are fast and free.

#### Acceptance Criteria

1. WHEN the Generator returns a Skill_Tree, THE Tree_Route SHALL store the Skill_Tree and its model id in the Tree_Cache under the Cache_Key of the request.
2. WHEN a Tree_Route request has a Cache_Key present in the Tree_Cache, THE Tree_Route SHALL respond with the cached Skill_Tree and the cached model id within 100 ms of receiving the request, without calling a Provider_Adapter.
3. THE Cache_Key SHALL include the Normalized_Hobby, the provider and the model of the Provider_Config used, so that the Model_Label of a cached tree names the model that produced the tree.
4. THE Tree_Cache SHALL hold at most 200 entries and, WHEN a new entry would exceed 200 entries, THE Tree_Cache SHALL remove the least recently used entry.
5. FOR ALL pairs of hobby inputs with equal Normalized_Hobby and equal provider and model, THE Cache_Key function SHALL return equal keys, and FOR ALL pairs that differ in Normalized_Hobby, provider or model, THE Cache_Key function SHALL return different keys (property).

### Requirement 7: Rate limit

**User Story:** As the operator, I want a cap on generations per visitor, so that the default key's cost stays bounded.

#### Acceptance Criteria

1. THE Rate_Limiter SHALL allow at most 10 Billable_Generations per client IP in any 60-minute sliding window.
2. IF a request would be the 11th Billable_Generation for a client IP within 60 minutes, THEN THE Tree_Route SHALL respond with HTTP status 429 and `{ "error": "rate_limited" }` without calling a Provider_Adapter.
3. WHEN a Tree_Route request is answered from the Tree_Cache, or uses a User_Config, THE Rate_Limiter SHALL leave the request out of the count.
4. WHEN the Start_Screen receives `{ "error": "rate_limited" }`, THE Start_Screen SHALL show the Friendly_Message "You've built a lot of trees this hour. Try again later, or add your own API key in Settings."
5. THE Rate_Limiter SHALL take the current time from an injected clock, so that tests control time.
6. FOR ALL sequences of request timestamps for one IP, THE Rate_Limiter SHALL allow a request exactly when fewer than 10 allowed requests from that IP have timestamps in the 60 minutes before the request (model-based property).

### Requirement 8: Timeout and errors

**User Story:** As a learner, I want a clear message when generation takes too long or fails, so that I'm never stuck on a spinner.

#### Acceptance Criteria

1. IF a Generator run, including the retry, has not finished 40 seconds after the Tree_Route received the request, THEN THE Tree_Route SHALL abort the pending provider call and respond with HTTP status 504 and `{ "error": "timeout" }`.
2. IF the Start_Screen has received no Tree_Route response 45 seconds after sending the request, THEN THE Start_Screen SHALL abort the request and show the Friendly_Message for `timeout`.
3. WHEN the Generator reports `provider_auth` or `provider_error`, THE Tree_Route SHALL respond with HTTP status 502 and `{ "error": <that Error_Code> }`.
4. WHEN the Start_Screen receives an Error_Code, THE Start_Screen SHALL leave the Generating_State, show the Friendly_Message for that Error_Code and keep the typed input so the user can submit again.
5. THE Start_Screen SHALL map every Error_Code to one Friendly_Message, and SHALL show the Friendly_Message for `generation_failed` for a response that is not valid JSON or has no known Error_Code.
6. WHEN the Start_Screen receives `provider_auth` for a request sent with a User_Config, THE Start_Screen SHALL show a Friendly_Message that tells the user to check the API key in Settings.

### Requirement 9: Start screen

**User Story:** As a first-time visitor, I want to type a hobby or tap an example and watch my tree get built, so that I see Pursio's value in the first 30 seconds.

#### Acceptance Criteria

1. THE Start_Screen SHALL show a text input labelled "What do you want to get better at?" limited to 60 characters, a submit button, and Example_Chips for "bouldering", "film photography" and "guitar".
2. WHEN the user submits a non-empty trimmed input, THE Start_Screen SHALL send a Tree_Route request and enter the Generating_State.
3. WHEN the user activates an Example_Chip, THE Start_Screen SHALL fill the input with the chip's hobby and send a Tree_Route request.
4. WHILE the Start_Screen is in the Generating_State, THE Start_Screen SHALL show "Building your skill tree…", disable the input, the submit button and the Example_Chips, and announce the state to screen readers through a live region.
5. WHERE LLM_Settings contain a non-empty API key, THE Start_Screen SHALL send the API key in the Key_Header and the saved provider and model in the request body.
6. THE Start_Screen SHALL show a link to the Settings_Page.

### Requirement 10: Opening and saving the generated path

**User Story:** As a learner, I want my new tree to open as a path and still be there when I return, so that I can keep walking it.

#### Acceptance Criteria

1. WHEN the Tree_Route returns a Skill_Tree, THE Start_Screen SHALL save the Skill_Tree and model id as the Generated_Tree in localStorage, replacing any earlier Generated_Tree, and navigate to `/path`.
2. WHEN a new Generated_Tree is saved, THE Path_View SHALL start the Generated_Tree with empty Progress, and Progress for the Sample_Tree shown at `/path?demo=1` SHALL stay separate from Generated_Tree Progress.
3. WHEN `/path` loads without the `demo=1` query and a Generated_Tree is saved, THE Path_View SHALL render the Generated_Tree with the existing path components and the existing Progress_Store behaviour.
4. WHEN `/path?demo=1` loads, THE Path_View SHALL render the Sample_Tree exactly as specified in the `skill-path-ui` spec.
5. WHEN `/path` loads without the `demo=1` query and no Generated_Tree is saved, THE Path_View SHALL render the Sample_Tree.
6. IF the saved Generated_Tree is not valid JSON or the Tree_Loader rejects the saved value, THEN THE Path_View SHALL remove the saved Generated_Tree and render the Sample_Tree.
7. WHILE the Path_View shows a Generated_Tree, THE Path_View SHALL show the Model_Label "Generated with <model id>" in small `muted` text under the tree.
8. FOR ALL Skill_Trees accepted by the Tree_Loader and all model ids, saving a Generated_Tree and reading the Generated_Tree back SHALL return a deeply equal Skill_Tree and an equal model id (round-trip property).

### Requirement 11: Settings page

**User Story:** As a learner with my own API key, I want to choose provider, model and key in one place, so that generation uses my account and model.

#### Acceptance Criteria

1. THE Settings_Page SHALL show a provider choice of "Anthropic" or "OpenAI", a model dropdown of the Model_Presets for the chosen provider, and a "Custom model id" text field.
2. WHEN the "Custom model id" field holds non-whitespace text, THE Settings_Page SHALL use the trimmed custom model id as the model; otherwise THE Settings_Page SHALL use the selected Model_Preset.
3. WHEN the user changes the provider, THE Settings_Page SHALL select the first Model_Preset of the new provider.
4. THE Settings_Page SHALL show the API key in a password field with a "Show" button that toggles the field between hidden and visible text and a "Clear" button that empties the field and removes the saved API key.
5. WHEN the user changes the provider, model or API key, THE Settings_Page SHALL save the LLM_Settings to localStorage in this browser.
6. THE Settings_Page SHALL show the note "Your key is stored only in this browser and sent only to generate your tree."
7. IF the saved LLM_Settings are not valid JSON or do not match the LLM_Settings shape, THEN THE Settings_Page SHALL remove the saved value and show empty LLM_Settings with the first provider and its first Model_Preset.
8. FOR ALL valid LLM_Settings, serializing and then parsing the LLM_Settings SHALL return deeply equal LLM_Settings (round-trip property).

### Requirement 12: Test connection

**User Story:** As a learner who entered a key, I want to check that the key and model work, so that I find setup problems before generating.

#### Acceptance Criteria

1. WHILE the API key field on the Settings_Page is empty, THE Settings_Page SHALL disable the "Test connection" button.
2. WHEN the user activates "Test connection", THE Settings_Page SHALL send a request to the Test_Route with the API key in the Key_Header and the chosen provider and model in the request body, and SHALL send no request directly to a provider.
3. WHEN the Test_Route receives a valid request, THE Test_Route SHALL make one provider request through the Provider_Adapter's provider with a maximum output of 16 tokens and respond within 15 seconds.
4. WHEN the provider request succeeds, THE Test_Route SHALL respond with `{ "ok": true }` and THE Settings_Page SHALL show "OK".
5. IF the provider request fails or takes longer than 15 seconds, THEN THE Test_Route SHALL respond with `{ "ok": false, "error": <Error_Code> }` and THE Settings_Page SHALL show the Friendly_Message for that Error_Code.

### Requirement 13: Scope and tests

**User Story:** As a developer, I want this feature small and its logic tested, so that it ships within the hackathon without regressions.

#### Acceptance Criteria

1. THE feature SHALL add no new package dependency.
2. THE automated tests run by `yarn test` SHALL cover Normalized_Hobby, Cache_Key, the Tree_Cache size limit, the Rate_Limiter, the Generator retry and Not_A_Hobby_Signal handling with mocked Provider_Adapters, the Generated_Tree storage round trip and the LLM_Settings storage round trip.
3. THE automated tests SHALL call no real provider and SHALL include no Vue component tests.
4. THE existing tests from the `skill-path-ui` spec SHALL keep passing, and `yarn typecheck` SHALL pass.
5. WHEN the feature is finished, THE CHANGELOG.md SHALL gain entries under "## [Unreleased]" referencing "(spec: ai-skill-tree-generation)".
