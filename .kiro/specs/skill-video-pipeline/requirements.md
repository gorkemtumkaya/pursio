# Requirements Document

## Introduction

Skill Video Pipeline is a server-side pipeline that finds, checks and scores learning videos for each (hobby, Skill title, level, language). Scored results are cached in a Video_Pool and shared by every user with the same hobby, Skill title, Level and language. Because pools are shared, the Search_Queries, the search parameters, the Judge input and the stored Judge output depend only on the Pool_Key and on the Skill's text (its description, quests and Quick_Tip_Skill flag), never on the user. The user's Goal never changes a search. The Goal only changes the order of cached videos (Requirement 11), using a Goal_Class that is stored once at path generation. Two features read from that cache: skill video suggestions in the skill sheet (this spec) and the Feed (a later spec). No client code calls the Video_Provider.

The spec covers five parts: Search_Queries, the Quick_Tip_Skill flag and the Goal_Class written during path generation, the pipeline steps, the triggers that fill pools, quota and failure handling, and the "Watch" section in the skill sheet. It also covers recording Video_Events that the Feed will reuse.

Because pools are shared, a video is linked to a quest by the quest's text, not by a quest index or a Skill id, since quest order and Skill ids differ between users' paths. The Skill_Sheet shows a "Watch how" link only where the user's own quest text equals the stored matched quest text of a video, after Normalization.

The quota count, the queued fills, the retry schedule and the in-progress lease of each Pool_Key are stored in the project's database (Postgres via Supabase). They survive server restarts and are shared by all Server instances. These records are server-only and no Client can read or write them.

Existing context: skill trees are generated by the `ai-skill-tree-generation` spec (`server/utils/generator.ts`, `shared/types/skill-tree.ts`), shown by `skill-path-ui`, and progress is stored by `local-progress-data` and `accounts-cloud-save`. A quest is identified for progress by the pair (skill id, index 0 to 2), as in `QuestId` in `shared/types/progress.ts`. Skill ids differ between users' paths, so the Video_Pool never uses a Skill id or a quest index. The user enters the Goal only on the Settings page and chooses the user's language there. The default language is `en`, not the browser language. If the Goal and the language are not yet stored, the design phase must add them. The user's region is not used, because region is not part of the Pool_Key. The Level in the Pool_Key is the level of the path section that contains the Skill (beginner, intermediate or advanced), so every user who has a Skill with the same title in the same section level shares one pool.

A videos request of a Signed_In_User carries the path id and the Skill id in addition to the hobby, the Skill title and the Level. The Server loads the path of that user and takes the Search_Queries, the Quest_Texts and the Quick_Tip_Skill flag from the stored Skill, so that no Client can supply queries or quests for a shared pool.

Signed_Out_Users (demo mode) can read existing Video_Pools through the videos endpoint. The Server ranks them with the Goal_Class `none` and limits their requests by client IP address with the existing rate limiter. Only a request with a verified Access_Token can start a fill. A request of a Signed_Out_User never causes a provider call, a model call or a fill request.

WHEN the user's Language_Code is not `en` and the user-language pool holds fewer than 3 videos, the videos endpoint adds videos from the `en` pool of the same hobby, Skill title and Level after the user-language videos, and marks the pool language of each video.

Retries are driven only by the videos requests of Signed_In_Users and by a server-protected Drain_Route. A database scheduled job (pg_cron with pg_net) calls the Drain_Route every 20 seconds.

Secrets live only in server environment variables set in the local environment file. New keys are listed with placeholder values in the example environment file, which already has the YouTube API key entry. No new dependencies are added without asking first.

## Glossary

- **Pipeline**: The server-side process that runs Search, Details, Filter, Judge and Store for one Pool_Key.
- **Pipeline_Run**: One execution of the Pipeline for one Pool_Key. A Pipeline_Run makes one search call per Search_Query of the Skill (2 or 3 in total), then one details call and one Judge call (each skipped when no Candidates remain for it), then stores the Video_Pool.
- **Video_Provider**: A generic server interface with the operations `search` and `getDetails`.
- **YouTube_Provider**: The first Video_Provider implementation, using the YouTube Data API v3.
- **Judge**: The language-model call that scores candidate videos in one request.
- **Path_Generator**: The existing server code that builds a skill tree from a hobby.
- **Skill**: A node of a skill tree (`SkillNode`) with an id, a title, a description, three quests, Search_Queries and a Quick_Tip_Skill flag. The id is specific to one user's path.
- **Quest**: One of the three quests of a Skill, identified for progress by the Skill id and an index of 0, 1 or 2, and identified for video matching only by its Quest_Text.
- **Quest_Text**: The text of a Quest as shown to the user.
- **Level**: One of `beginner`, `intermediate`, `advanced`. The Level of a Skill is the level of the path section that contains the Skill (the section level), not the user's start level.
- **Goal**: The free-text goal the user entered, for example "climb V3 by summer".
- **Goal_Class**: The class of a Goal, exactly one of `targeted`, `casual` or `none`. The Path_Generator assigns it once per path and stores it with the path. A path with no stored Goal_Class has the Goal_Class `none`.
- **Targeted_Goal**: A Goal with the Goal_Class `targeted`, which names a target or deadline.
- **Casual_Goal**: A Goal with the Goal_Class `casual`, which expresses fun or no target, for example "just for fun".
- **Search_Queries**: The 2 or 3 video search strings stored with a Skill. They depend only on the hobby, the Skill and the Level.
- **Quick_Tip_Skill**: A Skill whose stored quick-tip flag is true. The Path_Generator sets the flag (a boolean) for every Skill. A Quick_Tip_Skill may have videos shorter than 60 seconds. A Skill with no stored flag is not a Quick_Tip_Skill.
- **Candidate**: A video returned by search and not yet dropped by Filter or Judge.
- **Punctuation**: Any character in a Unicode punctuation category (the categories whose code starts with P: Pc, Pd, Ps, Pe, Pi, Pf, Po). Letters and digits of any script are not Punctuation.
- **Normalized**: Converted to lowercase, then with every Punctuation character removed, then with leading and trailing whitespace removed and each run of whitespace collapsed to one space. Letters and digits of any script are kept.
- **Language_Code**: The primary language subtag of the user's language, in lowercase (for example `en` for `en-US`, `pt` for `pt-BR`). WHERE the user has not chosen a language, the Language_Code is `en`. WHERE the language value is malformed (it has no valid primary subtag), the Language_Code is `und`.
- **Style**: The Judge's classification of a video, exactly one of `drill`, `technique`, `explainer` or `approachable`.
- **Matched_Quest_Text**: The Judge's `best_matching_quest_text` for a video: the text of the quest that the video best matches, or null.
- **Video_Pool**: The stored, scored list of videos for one Pool_Key, with the scores, Styles, Matched_Quest_Texts and details.
- **Pool_Key**: The tuple of the Normalized hobby, the Normalized Skill title, the Level (the section level) and the Language_Code. The Pool_Key contains no Skill id, no quest index, no region and no user identifier.
- **Pool_Expiry**: 7 days (604800 seconds) after the Video_Pool was stored.
- **Stale_Pool**: A Video_Pool whose age (time since its stored time) is greater than or equal to Pool_Expiry. A Stale_Pool is still served until a refresh succeeds and replaces it.
- **Fresh_Pool**: A Video_Pool whose age is less than Pool_Expiry.
- **Pipeline_State**: The records of the quota count, the queued fills, the retry schedule and the Run_Leases, stored in the database and used only by the Server.
- **Run_Lease**: The database-backed lock that marks a Pipeline_Run for one Pool_Key as in progress, with the time it was taken.
- **Lease_Timeout**: 5 minutes (300 seconds) after a Run_Lease was taken.
- **Current_Window**: The user's current Skill and the next 2 Skills on the path.
- **Pacific_Day**: A calendar day in the America/Los_Angeles time zone, from 00:00:00 to the next 00:00:00 in that zone, with daylight saving time applied. This matches the day used for the provider quota reset.
- **Daily_Quota**: The provider quota limit per Pacific_Day, set by server configuration. Search costs 100 units and a details call costs 1 unit.
- **Quota_Threshold**: 90 percent of the Daily_Quota.
- **Skill_Sheet**: The bottom sheet (mobile) or side panel (desktop) that shows a Skill's quests.
- **Watch_Section**: The section in the Skill_Sheet that lists suggested videos.
- **Video_Card**: A card showing the thumbnail, title, channel and duration of one video.
- **Embed_Player**: The inline player using the provider's privacy-enhanced embed.
- **Source**: The surface that produced a Video_Event, exactly one of `skill_sheet` or `feed`.
- **Video_Event**: A record per user, video and Source with the fields played time, watched seconds, finished, saved, Saved_Time, skipped, Source and updated time.
- **Finished**: A video state reached when the watched seconds are at least 80 percent of the duration.
- **Skipped**: A video state reached when the Video_Card was in view for 2 seconds or more without being played.
- **Client**: The browser application.
- **Server**: The Nitro server code under `server/`. Several Server instances may run at the same time and share the same database.
- **System**: The Client and the Server together.
- **Access_Token**: The sign-in token of a user, sent with a request to the Server and verified by the Server.
- **Signed_In_User**: A user whose request carries an Access_Token that the Server verifies.
- **Signed_Out_User**: A user whose request carries no Access_Token (demo mode).
- **Saved_Time**: The time of the last save or removal of a save of a video by a user, stored in the Video_Event field `savedAt`. It is null when the user never saved the video. Null is earlier than every time.
- **User_Language_Pool**: The Video_Pool whose Pool_Key has the user's Language_Code.
- **English_Pool**: The Video_Pool whose Pool_Key has the same Normalized hobby, Normalized Skill title and Level as the User_Language_Pool and the Language_Code `en`.
- **Pool_Language**: The Language_Code in the Pool_Key of the Video_Pool that a returned video came from.
- **Fallback_Condition**: The condition that the Language_Code is not `en` and the User_Language_Pool holds fewer than 3 videos. A missing User_Language_Pool holds 0 videos.
- **Fallback_Videos**: The videos from the English_Pool that the videos endpoint returns after the User_Language_Pool videos under Requirement 10.
- **Drain_Route**: The Server route that runs due queued fills and is protected by a secret kept in server environment variables.

## Requirements

### Requirement 1: Search queries, Quick_Tip_Skill flag and Goal class during path generation

**User Story:** As a learner, I want video searches written for my skill, hobby and level, short-tip skills marked, and my goal classified once, so that the videos I see fit what I am learning and are shared with other learners of the same skill.

#### Acceptance Criteria

1. WHEN the Server generates a path, THE Path_Generator SHALL return a minimum of 2 and a maximum of 3 Search_Queries for every Skill in the path.
2. THE Path_Generator SHALL write each Search_Query as a non-empty string of 3 to 100 characters that contains the hobby name or the Skill name.
3. THE Path_Generator SHALL write each Search_Query using only the hobby, the Skill and the Skill's Level as inputs, and SHALL make the 2 or 3 Search_Queries of one Skill pairwise distinct (case-insensitive).
4. WHERE the Level is beginner, THE Path_Generator SHALL include at least one of the terms "for beginners", "first" or "basics" in at least 1 Search_Query of each Skill.
5. WHERE the Level is intermediate, THE Path_Generator SHALL include at least one of the terms "drills", "technique" or "common mistakes" in at least 1 Search_Query of each Skill.
6. WHERE the Level is advanced, THE Path_Generator SHALL include at least one of the terms "advanced", "training" or "breakdown" in at least 1 Search_Query of each Skill.
7. WHEN the Path_Generator generates the same Skill for a beginner Level and for an advanced Level, THE Path_Generator SHALL return Search_Query sets that are not identical, so that at least 1 Search_Query differs between the two sets.
8. WHEN the Path_Generator writes Search_Queries for the same hobby, Skill and Level with two different Goals, THE Path_Generator SHALL return identical Search_Queries for both Goals.
9. WHEN the Path_Generator writes Search_Queries, THE Path_Generator SHALL receive no Goal value in its input for query writing.
10. IF the model returns fewer than 2 or more than 3 Search_Queries for a Skill, or returns a Search_Query that is empty or longer than 100 characters, THEN THE Path_Generator SHALL treat the response as invalid and apply the existing generation validation and retry rules, without storing the invalid Search_Queries.
11. WHEN the Server generates a path, THE Path_Generator SHALL classify the user's Goal once as `targeted`, `casual` or `none`, and THE System SHALL store that Goal_Class with the path.
12. IF the Goal is empty, or the classification is missing or is not one of `targeted`, `casual` or `none`, THEN THE System SHALL store the Goal_Class `none` for the path, and SHALL treat a path with no stored Goal_Class as having the Goal_Class `none`.
13. WHEN the Path_Generator returns a valid path, THE System SHALL store the Search_Queries with their Skill, in the order returned.
14. WHEN the Server generates a path, THE Path_Generator SHALL return a boolean Quick_Tip_Skill flag for every Skill in the path, decided using only the hobby, the Skill and the Level as inputs.
15. IF the model returns a Quick_Tip_Skill flag that is missing or is not a boolean for any Skill, THEN THE Path_Generator SHALL treat the response as invalid and apply the existing generation validation and retry rules, without storing the invalid flag.
16. WHEN the Path_Generator returns a valid path, THE System SHALL store the Quick_Tip_Skill flag with its Skill, in the order returned.
17. THE System SHALL treat a Skill of an existing path that has no stored Quick_Tip_Skill flag as having the flag value false.
18. WHEN the Pipeline needs Search_Queries for a Skill that has none stored, THE Pipeline SHALL generate 2 or 3 Search_Queries once for that Skill from the hobby, the Skill and the Level, and store them with the Skill.
19. IF the Pipeline fails to generate Search_Queries for a Skill that has none, THEN THE Pipeline SHALL leave the Skill unchanged with no Search_Queries stored and SHALL NOT retry generation for that Skill within the same Pipeline_Run.
20. FOR ALL valid Skill trees, serializing then parsing the Skill tree SHALL produce an equivalent tree, including every Skill's Search_Queries in the same order, every Skill's Quick_Tip_Skill flag and the Goal_Class (round-trip property).

### Requirement 2: Video provider abstraction

**User Story:** As a developer, I want the video provider behind a generic interface, so that another provider can replace YouTube without changing the Pipeline.

#### Acceptance Criteria

1. THE Server SHALL define the Video_Provider interface in its own server module, with exactly two operations: `search`, which takes a text query and a maximum result count of 1 to 50 and returns a list of video results, and `getDetails`, which takes a list of 1 to 50 video identifiers and returns the details for each identifier.
2. THE YouTube_Provider SHALL implement the Video_Provider interface using the YouTube Data API v3.
3. THE Pipeline SHALL call the provider only through the Video_Provider interface, and no Pipeline module SHALL import YouTube_Provider or reference YouTube-specific types, except the single module that selects the active provider.
4. THE Server SHALL read the provider API key only from server environment variables.
5. IF the provider API key is missing or empty when the Server calls `search` or `getDetails`, THEN THE YouTube_Provider SHALL fail the call with an error indicating the provider is not configured, make no request to the YouTube Data API v3, and leave previously stored data unchanged.
6. IF the YouTube Data API v3 returns an error, a quota-exceeded response, or no response within 10 seconds, THEN THE YouTube_Provider SHALL fail the call with an error indicating the failure category (not configured, quota exceeded, timeout or upstream error), without retrying more than once, and without including the API key in the error. The Pipeline handles the quota exceeded category under Requirement 9, criterion 5.
7. THE System SHALL keep the provider API key out of the repository, the Client bundle, runtime public config, every Server response and every log output.
8. THE System SHALL list every new environment key in the example environment file with a placeholder value and no real secret.
9. THE Client SHALL send no request to any provider API endpoint and, apart from the requests listed in Requirement 12, criterion 4 (the embed itself, the provider's player script and the provider's thumbnails), no request to any provider-owned host.

### Requirement 3: Search step

**User Story:** As a learner, I want the search to return only embeddable, safe, language-matched videos, so that I can watch them inside Pursio.

#### Acceptance Criteria

1. WHEN the Pipeline runs for a Skill, THE Pipeline SHALL run each of the Skill's Search_Queries exactly once per Pipeline_Run, with a maximum of 5 Search_Queries per Skill.
2. WHEN THE YouTube_Provider sends a search, THE YouTube_Provider SHALL set type to video, embeddable to true and safeSearch to strict on that search.
3. WHEN THE YouTube_Provider sends a search, THE YouTube_Provider SHALL set relevanceLanguage on that search to the Language_Code (the primary subtag of the user's language).
4. IF the Language_Code is `und`, THEN THE YouTube_Provider SHALL omit relevanceLanguage from the search and SHALL still send the search.
5. THE YouTube_Provider SHALL request a maximum of 10 results per search.
6. THE Pipeline SHALL build every search from only the Search_Query text, the Language_Code and the fixed parameters in criteria 2 and 5, so that no search parameter depends on anything outside the Pool_Key, and no search carries a regionCode or any other region value.
7. WHEN all searches for a Skill have returned, THE Pipeline SHALL merge the results into one Candidate list that contains each video id exactly once, keeping the first occurrence in Search_Query order.
8. IF a search fails or does not return within 10 seconds, THEN THE Pipeline SHALL discard that search's results, continue with the remaining searches, and merge the results of the searches that succeeded, subject to criteria 9 and 11.
9. IF every search for a Skill fails (error response or no response within 10 seconds), THEN THE Pipeline SHALL treat the run as a provider failure under Requirement 9, produce no Candidates, store no Video_Pool and keep any existing Video_Pool unchanged.
10. IF every search for a Skill succeeds and the searches return zero results in total, THEN THE Pipeline SHALL produce an empty Candidate list, skip the details and Judge steps and store an empty Video_Pool for the Pool_Key under Requirement 7, criterion 1.
11. IF at least one search for a Skill fails and the searches that succeeded return zero results in total, THEN THE Pipeline SHALL treat the run as a provider failure under Requirement 9 and store no Video_Pool.

### Requirement 4: Details step

**User Story:** As a learner, I want accurate video facts, so that length and language checks are reliable.

#### Acceptance Criteria

1. WHEN the Candidate list is merged, THE Pipeline SHALL request duration, view count, like count, publish date, default audio language, caption availability and embeddable status for all Candidates, in batched details calls of at most 50 Candidates each.
2. WHEN the details response for a Candidate contains a value for a requested field, THE Pipeline SHALL attach that value to the Candidate.
3. IF a requested field is absent from the details response for a Candidate (for example, hidden like count or no default audio language), THEN THE Pipeline SHALL mark that field as unknown on the Candidate and keep the Candidate in the list.
4. IF a Candidate is missing from the details response, THEN THE Pipeline SHALL drop that Candidate from the list.
5. IF the details call fails, returns an error response, or does not respond within 10 seconds, THEN THE Pipeline SHALL stop the run without passing any Candidates to the next step and apply the failure handling in Requirement 9.
6. IF the merged Candidate list is empty, THEN THE Pipeline SHALL skip the details call and continue with an empty list.

### Requirement 5: Filter step

**User Story:** As a learner, I want videos that are the right length and language, so that I do not waste time on unsuitable ones.

#### Acceptance Criteria

1. WHEN the Filter step evaluates a Candidate, THE Pipeline SHALL drop the Candidate if its duration is greater than 1500 seconds (25 minutes).
2. WHEN the Filter step evaluates a Candidate for a Skill whose stored Quick_Tip_Skill flag is false or missing, THE Pipeline SHALL drop the Candidate if its duration is less than 60 seconds.
3. WHEN the Filter step evaluates a Candidate for a Skill whose stored Quick_Tip_Skill flag is true, THE Pipeline SHALL keep the Candidate regardless of how short its duration is, provided it has a duration greater than 0 seconds and passes the other Filter step checks.
4. WHEN the Filter step evaluates a Candidate that has a default audio language, THE Pipeline SHALL drop the Candidate if the primary subtag of that language differs from the Language_Code, comparing case-insensitively (so that `en-US` matches `en` and `pt-BR` matches `pt`).
5. WHEN the Filter step evaluates a Candidate that has no default audio language, or the Language_Code is `und`, THE Pipeline SHALL keep the Candidate for the Judge step.
6. WHEN the Filter step evaluates a Candidate, THE Pipeline SHALL drop the Candidate if it is not embeddable.
7. IF the Filter step drops every Candidate for a Skill, THEN THE Pipeline SHALL pass an empty Candidate list to the next step and SHALL NOT raise an error.

### Requirement 6: Judge step

**User Story:** As a learner, I want only real instructional videos that teach my skill at my level, so that suggestions are useful.

#### Acceptance Criteria

1. WHEN Filter leaves one or more Candidates, THE Pipeline SHALL send all of them to the Judge in a single model call.
2. THE Pipeline SHALL send, for each Candidate, the title, the description truncated to its first 500 characters (descriptions of 500 characters or fewer sent unchanged), the channel and the duration.
3. THE Pipeline SHALL send, with the Candidates, the hobby, the Skill title, the Skill description, the Quest_Text of each of the Skill's quests and the Level, with no quest index and no quest identifier.
4. THE Judge SHALL return, for each Candidate, `teaches_this_skill` as a number from 0 to 1 inclusive, `level_fit` as a number from 0 to 1 inclusive, `is_instruction` as a boolean, `style` as exactly one of `drill`, `technique`, `explainer` or `approachable`, and `best_matching_quest_text` as a string or null.
5. WHEN the Judge returns a valid response, THE Pipeline SHALL drop each Candidate with `is_instruction` false.
6. WHEN the Judge returns a valid response, THE Pipeline SHALL drop each Candidate with `teaches_this_skill` below 0.5, and SHALL keep each Candidate with `teaches_this_skill` of exactly 0.5 or higher, provided `is_instruction` is true.
7. IF the Judge response is not valid for the schema in criterion 4 (including a missing field, a missing `style`, a `style` that is not one of the four values, a missing `best_matching_quest_text`, a `best_matching_quest_text` that is neither a string nor null, a wrong type, a number outside 0 to 1, or output that cannot be parsed), THEN THE Pipeline SHALL discard the whole response, keep no Candidates from it, and treat it as a model failure under Requirement 9.
8. IF the Judge response omits a Candidate that was sent, THEN THE Pipeline SHALL drop that Candidate and keep the evaluation of the remaining Candidates.
9. IF a kept Candidate's `best_matching_quest_text` is a string whose Normalized form does not equal the Normalized Quest_Text of any quest sent to the Judge, THEN THE Pipeline SHALL store null as the Matched_Quest_Text of that Candidate and SHALL keep the Candidate.
10. IF the Judge response contains an entry that matches no Candidate that was sent, THEN THE Pipeline SHALL ignore that entry.

### Requirement 7: Store step and cache sharing

**User Story:** As the product owner, I want results shared across users, so that provider and model costs stay low.

#### Acceptance Criteria

1. WHEN the Judge step completes, or WHEN the Judge step is skipped because no Candidates remain and no failure occurred, THE Pipeline SHALL store the scored Video_Pool (an empty Video_Pool when no videos remain) under its Pool_Key with, for each video, the Judge score, the `style`, the Matched_Quest_Text, the video details and the stored time.
2. THE Video_Pool SHALL contain each video id at most once.
3. THE Video_Pool SHALL contain only videos that passed Filter and Judge.
4. WHEN the age of a Video_Pool is greater than or equal to Pool_Expiry (604800 seconds), THE System SHALL treat the Video_Pool as a Stale_Pool, SHALL start a refresh for its Pool_Key, and SHALL keep serving the Stale_Pool until a refresh succeeds and replaces it.
5. WHEN a Video_Pool exists for a Pool_Key and its age is less than Pool_Expiry, THE Pipeline SHALL return that Video_Pool and make zero provider calls and zero model calls.
6. WHEN two or more users request the same Pool_Key while no Fresh_Pool is stored for it, THE Pipeline SHALL execute exactly one Pipeline_Run for that Pool_Key, consisting of one search call per Search_Query of the Skill (2 or 3 in total, not per user), one details call and one Judge call, and SHALL return the same Video_Pool to every requesting user, even when the users' Skill ids differ.
7. WHEN a Stale_Pool for a Pool_Key is requested, THE Pipeline SHALL execute a new Pipeline_Run for that Pool_Key and replace the Stale_Pool with the new Video_Pool only when the run succeeds through the store step.
8. WHILE a Run_Lease exists in the database for a Pool_Key and its age is less than the Lease_Timeout (300 seconds), THE Pipeline SHALL attach every later request for the same Pool_Key, on any Server instance, to that run and SHALL NOT start another Pipeline_Run for that Pool_Key.
9. THE System SHALL store the Video_Pool in shared storage that is not scoped to one user, so that a Video_Pool stored for one user's request is readable by every other user's request for the same Pool_Key.
10. IF a run for a Pool_Key fails before the store step completes, THEN THE Pipeline SHALL store no Video_Pool for that Pool_Key, SHALL release the Run_Lease, SHALL return an error indication to every request attached to that run, and SHALL keep any previously stored Video_Pool, including a Stale_Pool, for that Pool_Key unchanged and servable.
11. WHEN two requests differ in the Normalized hobby, the Normalized Skill title, the Level or the Language_Code, THE System SHALL use different Pool_Keys and different Video_Pools for them.
12. WHEN the age of a Run_Lease reaches the Lease_Timeout (300 seconds) before its run has finished, THE Pipeline SHALL treat the Run_Lease as expired, so that a request on any Server instance MAY take the Run_Lease and start a new Pipeline_Run for that Pool_Key, and the Pipeline SHALL NOT let the run with the expired Run_Lease replace a Video_Pool stored by the run that took over.
13. WHEN two requests have a hobby or a Skill title that differ only by case, whitespace or Punctuation, and have the same Level and Language_Code, THE System SHALL use the same Pool_Key and the same Video_Pool for them.
14. WHEN a Run_Lease is taken, held or released, THE Pipeline SHALL record it in the database, so that the lock works across Server instances and survives a Server restart.

### Requirement 8: Pipeline triggers

**User Story:** As a learner, I want videos ready when I open a skill, without slowing path creation.

#### Acceptance Criteria

1. WHEN a path is created, THE Server SHALL start a background fill of the Video_Pools of every Skill in the Current_Window that has no Fresh_Pool.
2. WHEN the Server starts the background fill for a new path, THE Server SHALL return the created path to the client without waiting for the fill to finish.
3. WHEN the current Skill of a Signed_In_User changes, THE Server SHALL start a background fill of the Video_Pools of every Skill in the new Current_Window that has no Fresh_Pool, without delaying the response that reports the change.
4. WHEN the Current_Window has fewer than 3 Skills remaining, THE Pipeline SHALL fill the Video_Pools of only those remaining Skills and SHALL NOT create Video_Pools for Skills outside the path.
5. THE Pipeline SHALL fill Video_Pools only for Skills in the Current_Window.
6. WHEN a Skill in the Current_Window has a Fresh_Pool for its Pool_Key, THE Pipeline SHALL skip that Skill and SHALL NOT fetch or replace its videos.
7. IF the background fill fails for a Skill, THEN THE Pipeline SHALL leave the path and the user's progress unchanged, SHALL leave that Skill without a new Video_Pool, and SHALL continue filling the remaining Skills in the Current_Window.
8. IF a Skill in the Current_Window has no Video_Pool at the moment a Signed_In_User opens it, THEN THE Server SHALL start a fill for that Skill's Video_Pool and SHALL return a response indicating that videos are not yet available.
9. WHEN the Pipeline fills a Skill, THE Pipeline SHALL derive the Pool_Key from the Skill's title, the path's hobby, the Skill's Level (the section level) and the user's Language_Code, and SHALL NOT use the Skill id.
10. WHEN a Signed_Out_User opens a Skill, THE Server SHALL start no fill, make no provider call and make no model call, as stated in Requirement 10, criterion 11.

### Requirement 9: Quota and failure handling

**User Story:** As the product owner, I want quota use bounded and failures contained, so that the product keeps working when the provider or model fails.

#### Acceptance Criteria

1. THE Pipeline SHALL count provider quota use per Pacific_Day, adding 100 units for each search call and 1 unit for each details call, including calls that return an error.
2. WHEN a new Pacific_Day starts (00:00:00 America/Los_Angeles, daylight saving time applied), THE Pipeline SHALL reset the daily count to 0 and release queued fills for retry.
3. WHILE the counted quota use is at or above the Quota_Threshold, THE Pipeline SHALL start no new search call.
4. WHILE the counted quota use is below the Quota_Threshold, THE Pipeline SHALL start a search call only if the counted use plus 100 units stays at or below the Daily_Quota.
5. WHEN the provider returns a quota-exceeded response, THE Pipeline SHALL set the counted quota use of the current Pacific_Day to the Daily_Quota, so that no further search call starts until the next Pacific_Day.
6. WHEN a search call is blocked by the Quota_Threshold or by the Daily_Quota check, THE Pipeline SHALL queue the fill for the Pool_Key and retry it after the next America/Los_Angeles midnight (the start of the next Pacific_Day), and SHALL keep serving the existing Stale_Pool or empty list in the meantime.
7. THE Server SHALL read the Daily_Quota from server configuration as a positive integer, with a default of 10000 units when the value is missing or not a positive integer.
8. IF the provider fails (error response, no response within 10 seconds, or every search of the run fails under Requirement 3, criterion 9) and a Stale_Pool exists, THEN THE Server SHALL keep serving the Stale_Pool unchanged and schedule a retry.
9. IF the model fails (error response, or no response within 30 seconds, or output that cannot be used) and a Stale_Pool exists, THEN THE Server SHALL keep serving the Stale_Pool unchanged and schedule a retry.
10. IF the provider or the model fails and no Video_Pool exists, THEN THE Server SHALL return an empty video list for the Skill without an error indication to the client and schedule a retry.
11. IF the Pipeline fails, THEN THE Server SHALL complete path creation and path loading with the same success response and data as when the Pipeline is not run, with no error caused by the Pipeline.
12. WHEN a retry is scheduled, THE Pipeline SHALL wait longer than the previous wait before each further retry of the same Pool_Key, SHALL start no more than 5 retry attempts per Pool_Key per Pacific_Day, and SHALL start no retry whose call would exceed the limits in criteria 3 and 4.
13. IF a run fails, THEN THE Server SHALL log the failure, including the Pool_Key and the failure type, without the API key or any other secret value.
14. THE Server SHALL store the Pipeline_State (the quota count per Pacific_Day, the queued fills, the retry schedule with the retry attempt count of each Pool_Key, and the Run_Leases) in the project's database (Postgres via Supabase), so that the Pipeline_State survives a Server restart and is shared by all Server instances.
15. WHEN a Server instance restarts, THE Pipeline SHALL continue from the stored Pipeline_State, keeping the counted quota use, the queued fills, the retry schedule and the unexpired Run_Leases that were stored before the restart.
16. WHEN two or more Server instances start search calls at the same time, THE Pipeline SHALL reserve the 100 units of each search call in the stored quota count before the call starts, so that the counted quota use never exceeds the Daily_Quota because of concurrent calls.
17. THE System SHALL keep the Pipeline_State readable and writable only by the Server, and SHALL deny every Client read and write of Pipeline_State records and include no Pipeline_State record in any Server response.
18. THE Pipeline SHALL run queued fills and retries whose scheduled time has been reached only after the Server has served a videos request of a Signed_In_User (at most 2 such fills per request) and when the Drain_Route is called (at most 5 such fills per call).
19. THE System SHALL require no scheduled retry job for correct operation.
20. WHEN a request reaches the Drain_Route with the secret that is set in server environment variables, THE Server SHALL run due fills as stated in criterion 18.
21. IF a request to the Drain_Route has a missing or wrong secret, or no secret is set in server environment variables, THEN THE Server SHALL run no fill, make no provider call, make no model call and return an error response.
22. WHEN the Server has served a videos request of a Signed_Out_User, THE Pipeline SHALL run no queued fill and no retry as a result of that request.

### Requirement 10: Videos endpoint

**User Story:** As a learner, I want the skill sheet to get its videos from one server call, so that the Client never touches the provider.

#### Acceptance Criteria

1. WHEN the Client requests videos for one Skill, THE Server SHALL resolve the User_Language_Pool by the Pool_Key built from the hobby, the Skill's title, the Skill's Level (the section level) and the user's Language_Code, and SHALL return the videos from that Video_Pool in ranked order (Requirement 11), followed by any Fallback_Videos under criterion 15, with a maximum of 12 videos per response. WHERE the request has no language, THE Server SHALL use the Language_Code `en`.
2. WHEN the endpoint is called, THE Server SHALL read the Video_Pool and respond without starting a provider call or a model call in the request path, within 500 ms at the 95th percentile.
3. WHEN the endpoint finds no Video_Pool or a Stale_Pool, THE Server SHALL return the videos currently available (an empty list if none) together with a flag stating whether a fill is in progress.
4. WHEN the endpoint serves a Signed_In_User and finds no Video_Pool or a Stale_Pool for the Pool_Key of the User_Language_Pool and no fill is already in progress for that Pool_Key (no unexpired Run_Lease exists), THE Server SHALL request exactly one background fill (one Pipeline_Run) for that Pool_Key and set the fill-in-progress flag to true in the same response.
5. IF the request body or query is invalid (missing or empty hobby, missing or empty Skill title, hobby or Skill title longer than 100 characters, missing Level, Level not one of the defined Levels, or, for a Signed_In_User, a missing or empty path id or Skill id), THEN THE Server SHALL return a 400 response with an error code identifying the invalid field, make no provider call and request no fill.
6. IF a request exceeds the rate limit of the existing rate limiter, which counts a Signed_In_User by user and a Signed_Out_User by client IP address, THEN THE Server SHALL reject the request with a rate-limit error response, make no Video_Pool read and request no fill.
7. THE Server SHALL exclude the API key from every response and every Client bundle.
8. THE Server SHALL include in each returned video its Matched_Quest_Text (a string or null) so that the Skill_Sheet can match it to the user's quests.
9. WHEN a request carries no Access_Token, THE Server SHALL treat it as a request of a Signed_Out_User, read the existing Video_Pools, rank the videos with the Goal_Class `none`, and return the videos (including Fallback_Videos under criterion 15 from an existing English_Pool) with the fill-in-progress flag false.
10. IF a request carries an Access_Token that the Server cannot verify, THEN THE Server SHALL return a 401 response, make no Video_Pool read, make no provider call and request no fill.
11. WHILE a request comes from a Signed_Out_User, THE Server SHALL make no provider call, make no model call and request no fill, whether the Video_Pool is missing, stale or fresh.
12. IF a request of a Signed_Out_User finds no Video_Pool, THEN THE Server SHALL return an empty video list with the fill-in-progress flag false.
13. WHEN the Server requests a fill for a Signed_In_User, THE Server SHALL load the path of that user with the user's own access, find the Skill by the Skill id, and take the Search_Queries, the Skill description, the Quest_Texts and the Quick_Tip_Skill flag only from that stored Skill.
14. IF, before the Server requests a fill, the Skill identified by the Skill id is not in the path of the user, or the Normalized hobby, the Normalized Skill title or the Level of that stored Skill differs from the request, THEN THE Server SHALL return a 400 response with the error code identifying the field `skillId`, make no provider call and request no fill.
15. WHEN the Fallback_Condition holds, THE Server SHALL return the User_Language_Pool videos first, followed by Fallback_Videos from the English_Pool, until up to 12 videos are returned in total.
16. THE Server SHALL rank the Fallback_Videos by Requirement 11 within the English_Pool and SHALL place all Fallback_Videos after all User_Language_Pool videos.
17. THE Server SHALL include each video id at most once in a response, SHALL keep the User_Language_Pool copy when a video id is in both pools, and SHALL remove the duplicate before the limit of 12 videos is applied.
18. THE Server SHALL include in each returned video its Pool_Language.
19. WHEN the Fallback_Condition holds for a Signed_In_User, and the English_Pool is missing or is a Stale_Pool, and no unexpired Run_Lease exists for its Pool_Key, THE Server SHALL request exactly one background fill for the English_Pool, built from the same stored Skill under criterion 13 with the Language_Code `en`, in addition to any fill under criterion 4.
20. WHILE the Language_Code is `en` or the User_Language_Pool holds 3 or more videos, THE Server SHALL return no Fallback_Videos and SHALL request no fill of an English_Pool under criterion 19.
21. WHILE a fill is in progress or has been requested for the User_Language_Pool, or for the English_Pool under criterion 19, THE Server SHALL set the fill-in-progress flag to true.

### Requirement 11: Ranking and goal rerank

**User Story:** As a learner, I want the best videos for my skill and goal first, so that I watch the most useful ones.

#### Acceptance Criteria

1. THE Server SHALL compute a base score for each video in the Video_Pool as `teaches_this_skill` multiplied by `level_fit`, where both inputs and the resulting base score are numbers from 0.0 to 1.0 inclusive.
2. THE Server SHALL order the videos of a Video_Pool for a Skill by ranking score in descending order, where ranking score is the base score plus the goal rerank adjustment.
3. WHEN the Server applies the goal rerank, THE Server SHALL use only the cached Video_Pool and the Goal_Class stored with the user's path, and SHALL make zero new search requests.
4. WHERE the Goal_Class is `targeted`, THE Server SHALL give a positive goal rerank adjustment to videos whose Style is `drill` or `technique` and a goal rerank adjustment of 0 to all other videos.
5. WHERE the Goal_Class is `casual`, THE Server SHALL give a positive goal rerank adjustment to videos whose Style is `approachable` or whose duration is 900 seconds (15 minutes) or less, and a goal rerank adjustment of 0 to all other videos.
6. IF the Goal_Class is `none`, or is missing for an existing path, THEN THE Server SHALL set the goal rerank adjustment to 0 for every video, so that the order equals the order by base score.
7. THE Server SHALL limit each goal rerank adjustment to a range of 0.0 to 0.2 inclusive, so that a video whose base score is higher than another video's base score by more than 0.2 stays ranked above it.
8. IF two videos have equal ranking scores, THEN THE Server SHALL order them by ascending video id so that repeated requests with the same inputs return the same order.
9. THE Server SHALL return the full ranked list of the Video_Pool without capping it at 3, subject only to the maximum of 12 videos per response in Requirement 10, criterion 1, and IF the Video_Pool is empty, THEN THE Server SHALL return an empty list.
10. THE Server SHALL apply the goal rerank per request and SHALL NOT store the rerank result in the shared Video_Pool.
11. WHEN the Server returns Fallback_Videos, THE Server SHALL apply criteria 1 to 8 within each Video_Pool separately and SHALL place every User_Language_Pool video before every Fallback_Video, whatever their ranking scores.
12. WHEN the request comes from a Signed_Out_User, THE Server SHALL use the Goal_Class `none` for every Video_Pool, so that the order within each Video_Pool equals the order by base score.

### Requirement 12: Watch section in the skill sheet

**User Story:** As a learner, I want to watch a few good videos on a skill's sheet, so that I can learn without leaving Pursio.

#### Acceptance Criteria

1. WHEN the Skill_Sheet opens for a Skill and the Server returns 1 or more ranked videos (up to 12), THE Skill_Sheet SHALL show a Watch_Section containing the top-ranked videos of the received list in rank order, up to a maximum of 3 Video_Cards.
2. THE Video_Card SHALL show the thumbnail, the title, the channel and the duration in minutes and seconds (or hours, minutes and seconds for videos of 60 minutes or longer).
3. WHEN the user taps a Video_Card, THE Skill_Sheet SHALL replace that Video_Card's thumbnail with the Embed_Player for that video, inside the Skill_Sheet and without navigating away from Pursio, and the Embed_Player SHALL start playing the video immediately as a result of that tap.
4. THE Embed_Player SHALL use the provider's privacy-enhanced embed domain as the player host and SHALL load the video from that domain. THE Skill_Sheet SHALL load the provider's player script from the provider's standard domain and the Video_Card thumbnails from the provider's image host, and SHALL send no other request to a provider-owned host besides the embed itself.
5. WHILE no user action has requested a video (when the Skill_Sheet opens or a Video_Card renders), THE Skill_Sheet SHALL play no video. The Embed_Player is created only by a tap on a Video_Card (criterion 3) or by a "Watch how" link (criterion 12).
6. WHEN a video starts playing, THE Skill_Sheet SHALL pause or stop every other video in the Skill_Sheet, so that at most 1 video plays at any time.
7. WHILE the Server reports that a fill is in progress and the Skill has 0 videos, THE Skill_Sheet SHALL show the line "Finding videos for this skill" in the Watch_Section position.
8. WHILE the Server reports that no fill is in progress and the Skill has 0 videos, THE Skill_Sheet SHALL hide the Watch_Section.
9. WHEN the Server reports that a fill has finished while the Skill_Sheet is open, THE Skill_Sheet SHALL remove the "Finding videos for this skill" line and show either the Watch_Section with the resulting videos (1 to 3 Video_Cards) or no Watch_Section if the Skill has 0 videos.
10. IF the videos request fails, THEN THE Skill_Sheet SHALL hide the Watch_Section, SHALL show no error dialog that blocks the sheet, and SHALL keep the Skill's quests visible and operable (including marking quests complete).
11. WHEN the Skill_Sheet shows a Skill's Quests, THE Skill_Sheet SHALL show a "Watch how" link next to a Quest for the highest-ranked video among all videos the Skill_Sheet received (up to 12, including videos beyond the top 3) whose Normalized Matched_Quest_Text equals the Normalized Quest_Text of that Quest, and SHALL show no "Watch how" link next to a Quest for which no received video has a Normalized Matched_Quest_Text equal to its Normalized Quest_Text (including when every Matched_Quest_Text is null).
12. WHEN the user activates a "Watch how" link, THE Skill_Sheet SHALL show the linked video in the Embed_Player in the Watch_Section (in place of its Video_Card if the video is among the shown Video_Cards, otherwise above the Video_Cards), bring it into view in the Skill_Sheet, and the Embed_Player SHALL start playing the video immediately as a result of that activation.
13. WHEN a user plays or finishes a video, THE System SHALL leave the user's XP total, level and streak unchanged.
14. THE Watch_Section SHALL allow every Video_Card and every "Watch how" link to be reached with the Tab key and activated with the Enter key or the Space key, and SHALL expose for each Video_Card an accessible name that includes the video title, and for each "Watch how" link an accessible name that includes the video title and the Quest_Text of the Quest it relates to.
15. THE Watch_Section SHALL use only theme token utilities for color, font, radius and shadow, with no hardcoded values.
16. WHILE the user is signed out, THE Client SHALL send the videos request without an Access_Token, SHALL send no fill request, and SHALL show the Watch_Section only when the response contains 1 or more videos.
17. WHILE the user is signed out and the response contains 0 videos, THE Skill_Sheet SHALL hide the Watch_Section and SHALL NOT show the line "Finding videos for this skill".
18. WHERE the Pool_Language of a shown video differs from the user's Language_Code, THE Video_Card SHALL show the Pool_Language code as a label.

### Requirement 13: Video events

**User Story:** As the product owner, I want per-user video events recorded now, so that the Feed can reuse them later.

#### Acceptance Criteria

1. WHEN a user starts a video on a surface, THE System SHALL record a played event for that user, video and Source of that surface, with the time of the first play stored once and not overwritten by later plays.
2. WHILE a video is playing, THE System SHALL add the elapsed playback time to the watched seconds for that user, video and Source at intervals of 5 seconds or less, and SHALL also write the current value when the video pauses, ends, or the user leaves the page.
3. WHEN the watched seconds reach 80 percent or more of the video duration, THE System SHALL mark the video as Finished for that user, video and Source.
4. IF the video duration is unknown or 0 seconds, THEN THE System SHALL NOT mark the video as Finished.
5. WHEN a user saves a video, THE System SHALL record saved as true, with the Saved_Time and the updated time both set to the time of the save, for that user, video and the Source of the surface where the user saved it.
6. WHEN a user removes a saved video, THE System SHALL record saved as false, with the Saved_Time and the updated time both set to the time of the removal, for that user, video and the Source of the surface where the user removed it.
7. WHEN a Video_Card has been at least 50 percent visible in the viewport for 2 continuous seconds and the video has not been played by that user, THE System SHALL record skipped for that user, video and the Source of the surface that showed the Video_Card, and for no other Source.
8. WHEN a user plays a video that is recorded as skipped for the Source of the playing surface, THE System SHALL clear the skipped flag for that user, video and that Source.
9. THE System SHALL store at most one Video_Event record per user, video and Source, updated in place.
10. THE System SHALL keep watched seconds as a non-negative value that never decreases within one record, and SHALL keep a Finished mark once set.
11. WHEN a user is signed in, THE System SHALL store Video_Events in the user's cloud data under the existing row-level security, so that a user can read and write only their own records.
12. WHILE a user is not signed in, THE System SHALL store Video_Events locally.
13. WHEN a user signs in and local Video_Events exist, THE System SHALL move them to the user's cloud data, and for a user, video and Source that already has a cloud record SHALL keep the higher watched seconds, keep Finished if either record has it, and keep the saved value and the Saved_Time of the record with the later Saved_Time, independently of the other fields. WHEN both Saved_Times are equal, THE System SHALL keep saved as true if either record has it.
14. IF recording a Video_Event fails, THEN THE System SHALL keep the video playable, keep the unsent event stored locally, show no blocking error to the user, and retry the write at least once within 60 seconds and again on the next app start until it succeeds.
15. THE System SHALL use the same Video_Event record format, including the Source field, for the Skill_Sheet and the later Feed.
16. WHEN the System reads played time, watched seconds, Finished or saved for a user and video, THE System SHALL combine the records of all Sources: the earliest played time, the highest watched seconds, Finished if any record has it, and the saved value and Saved_Time of the record with the latest Saved_Time (saved as true when equal Saved_Times differ in saved).
17. THE System SHALL count a skipped flag for the Feed only from Video_Event records whose Source is `feed`, and SHALL NOT count a skipped flag from a record whose Source is `skill_sheet`.
18. FOR ALL Video_Event records, serializing then parsing the record SHALL produce an equivalent record, including its Source and its Saved_Time (round-trip property).
19. THE System SHALL change the saved value and the Saved_Time of a record only when the user saves or removes the video, so that plays, progress and skips leave both unchanged.
20. FOR ALL Video_Event records a and b for the same user, video and Source, merging a with b SHALL produce the same record as merging b with a (commutative property).

### Requirement 14: Verification

**User Story:** As a developer, I want tests for the pipeline's guarantees, so that regressions are caught.

#### Acceptance Criteria

WHEN two different users with different Skill ids, the same Skill title, the same hobby, the same Level and the same Language_Code each open the Skill, THE test suite SHALL verify that exactly 1 Pipeline_Run executes, that the fake Video_Provider receives exactly as many search calls as the Skill has Search_Queries (2 or 3) in total and not per user, one details call, that the fake Judge receives 1 call, and that both users receive the same Video_Pool.

19. THE test suite SHALL verify that a fake Judge response with a missing `best_matching_quest_text`, or a `best_matching_quest_text` that is neither a string nor null, is discarded as invalid, that no quest index or quest identifier is sent to the fake Judge, and that a `best_matching_quest_text` whose Normalized form equals no Normalized Quest_Text sent to the fake Judge is stored as null while the video is kept.

THE test suite SHALL verify that a user whose quest text differs from the stored Matched_Quest_Text sees no "Watch how" link for that quest, that a quest text equal to the Matched_Quest_Text after Normalization (differing only in case, spacing or Punctuation) gets a "Watch how" link, and that when several received videos match one quest the link points to the highest-ranked one.

## Out of scope

- The Feed itself and its ranking, which a later spec covers.
- Awarding XP for watching.
- Pools for Skills outside the Current_Window.
- Goal-specific searches or per-user Video_Pools (the Goal only reranks cached videos).
- Region-specific searches or region-specific Video_Pools (the region is not part of the Pool_Key).
- Linking videos to quests by quest index or by approximate text matching (only equal Normalized text counts).
- The database table design for the Pipeline_State, which the design phase defines.
- Providers other than YouTube.
- Photo or video progress logs.
- A scheduled retry job (retries are driven only by the videos requests of Signed_In_Users and by the Drain_Route).
- Goal entry on the new-hobby page (the Goal is entered only on the Settings page).
- Detecting the user's language from the browser (the default language is `en`).
